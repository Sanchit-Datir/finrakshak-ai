# Boundary Conditions

Claude (and humans) must flag any of these to the project owner when touched. Format:
**ID — condition → required handling.**

## Money & numbers

- **B-01 Floating-point money** → integer minor units only (`Money`). Reject non-integers/unsafe ints.
- **B-02 Currency mismatch** → never add/compare across currencies without explicit FX conversion; throw.
- **B-03 Overflow** → `Number.isSafeInteger` check after every arithmetic op; consider BigInt if totals may exceed 2^53.
- **B-04 Negative / zero amounts** → decide per field (contribution > 0; refund/adjustment may be negative). Ask the owner if unspecified.
- **B-05 Rounding** → define rounding rule (half-even vs half-up) explicitly when splitting or applying percentages; never silently truncate.

## Auth & authorization

- **B-06 Unauthenticated calls** → every callable rejects with `unauthenticated` first.
- **B-07 Cross-user access (IDOR)** → verify `ownerUid === request.auth.uid` server-side; don't trust IDs from the client.
- **B-08 App Check / abuse** → enforce App Check; rate-limit expensive callables (esp. Gemini).
- **B-09 Token expiry mid-session** → UI must handle `unauthenticated` by re-auth, not a blank error.

## Gemini / Vertex AI

- **B-10 Prompt size** → cap input (`GEMINI_LIMITS.maxPromptChars`); truncate or reject with a clear message.
- **B-11 Output size** → set `maxOutputTokens`; handle truncated output (finish reason `MAX_TOKENS`).
- **B-12 Empty / blocked / safety-filtered response** → treat as a handled failure, never as success.
- **B-13 Malformed / non-conforming output** → parse with zod; on failure retry once or return a graceful error; never trust free text.
- **B-14 Timeout, 429, 5xx** → bounded timeout, limited retries with exponential backoff + jitter; surface a retryable error.
- **B-15 Cost runaway** → per-user quotas and budget alerts on the GCP project before enabling in prod.
- **B-16 Prompt injection / PII** → delimit user data; don't send secrets or unnecessary PII to the model; don't log prompts.
- **B-17 Model/region availability** → model name and region come from config; verify availability before deploy; models get deprecated.

## Firestore

- **B-18 Document size** → 1 MiB per doc; don't store unbounded arrays — use subcollections.
- **B-19 Write rate** → ~1 write/sec sustained per document; use sharded counters/aggregation for hot totals.
- **B-20 Batch/transaction limits** → ≤ 500 ops per batch/transaction; chunk larger work.
- **B-21 Concurrency / lost updates** → use transactions or `FieldValue.increment` for balances; never read-modify-write outside a transaction.
- **B-22 Query limits** → always paginate (`limit` + cursor); `in` ≤ 30 values; composite indexes must exist; no unbounded reads.
- **B-23 Eventual client state** → handle offline/pending writes and permission-denied errors in the UI.
- **B-24 Idempotency** → retried functions / double-clicks must not double-record a transaction; use client-supplied idempotency keys / deterministic doc IDs.

## Input & data

- **B-25 Empty / whitespace / max-length strings** → trim, enforce min/max in the shared schema.
- **B-26 Unicode & injection** → normalise where comparing names; escape on render.
- **B-27 Dates & timezones** → store UTC instants; **"a day" is an Indian calendar day (IST, UTC+05:30, no DST)** by the owner's decision (17 Oct 2026). `istDate()` in `packages/shared/src/time.ts` is the one helper: the daily schedule (03:05 IST), listing history files, BigQuery `run_date` partitions and baselines, and per-user AI limits all use it; dates printed by sources are kept as published. Beware month-end when computing periods.
- **B-28 Duplicate creation** → decide uniqueness rules (e.g. fund name per owner) and enforce server-side.
- **B-29 Deletion** → soft-delete financial records; define cascade behaviour before implementing.

## Platform & deploy

- **B-30 Cloud Functions limits** → default timeout 60s (max 540s for HTTP/callable gen2 up to 3600s on some configs), cold starts, memory; long jobs go to Cloud Tasks/Pub/Sub.
- **B-31 Secrets & env** → no secrets in the web bundle (all `VITE_*` is public). Use Secret Manager for server secrets.
- **B-32 Firebase plan** → Functions + Vertex require the Blaze (pay-as-you-go) plan; confirm before deploy.
- **B-33 Security-rule regressions** → every rules change needs emulator tests; default-deny must remain.
- **B-34 Deployment region** → keep Functions, Firestore, and Vertex in compatible regions (latency, data residency).
- **B-67 Two Hosting sites, one build** → every deploy publishes the same build and config to `fund-tracer` and `finrakshak-ai` (Hosting targets in `.firebaserc`, one `firebase.json` entry each). The entries must stay identical apart from `target`; `web/src/lib/security-headers.test.ts` fails on drift. A new site's domain must be added to Auth authorized domains and the reCAPTCHA key (and any API-key website restrictions) by hand; until then sign-in and App Check fail closed there. Each deploy stores a version per site, so set release retention on both (cost). The `/graph-lab/` bundle (B-46) is public on both. See docs/DEPLOY.md.

## Public-data ingestion (`ingest/`)

- **B-35 Source access & terms** → honour robots.txt, never bypass CAPTCHA/login/403 blocks, keep ≥1.5 s per host and back off on 429/5xx; record terms on every raw artifact. ED and SFIO copyright policies require permission before reproduction — keep their documents internal (private bucket/repo) until permission is obtained. NSE/BSE need a licence.
- **B-36 Evidence status** → every event/claim/edge carries `fact | finding | allegation | inference`. ED attachments, SEBI interim orders and show-cause notices are allegations; insolvency is not fraud; NFRA findings concern auditors. Never upgrade a status in UI or Gemini output.
- **B-37 Entity resolution** → merge only on exact CIN or exact normalised name; fuzzy similarity only writes `entity_match_candidates` for human review. Common names (e.g. "The Urban Co-operative Bank Ltd.") keep the town to avoid false merges.
- **B-38 Personal data** → store people only in public professional roles (insolvency professional, audit engagement partner). Individual noticees/accused named in orders are not extracted. MCA registered-office addresses of small companies/LLPs are often residences: use them only to link companies, never publish them.
- **B-39 Large rupee amounts** → amounts are INR paise integers; values above `Number.MAX_SAFE_INTEGER` (~₹90 lakh crore) or with sub-paisa precision are rejected, not rounded.

## Relationship graph (graph lab, `ingest/src/graph`, `/graph-lab`)

- **B-40 Hubs and non-specific connectors** → big banks, regulators filing insolvency (e.g. RBI), batch notices naming many parties, busy insolvency professionals and shared service addresses connect thousands of unrelated companies. Their links are shown as weak and never chain networks; limits are `THRESHOLDS` in `ingest/src/graph/edges.ts` and need calibration on reviewed cases. A connection is never evidence of wrongdoing.
- **B-41 Graph size in the browser** → the graph lab loads one whole bundle (~36 MB JSON / ~5 MB gzip, 43k nodes for Maharashtra MCA + seed cases). National MCA coverage would multiply it; serve subgraphs from a backend before scaling, and keep the in-browser layout capped (`LAYOUT_CAP`).
- **B-42 Party role in proceedings** → `named_in` records that an organisation appears in an order or press release, not whether it is the accused, the victim or the complainant (e.g. a lender defrauded in a vehicle-loan case, or a company whose ex-director was arrested for cheating it). Any lending-risk flag built on enforcement records must show the source text for review and must not treat "named in" as "accused" until the role is extracted.
- **B-43 Public-record snapshot age and conflicting sources** → the application's public-records check reads a local snapshot (`data/graph`), not live MCA21/IBBI. Every result shows the dataset build date and is saved with it; when MCA status and IBBI records disagree (e.g. "Active" in MCA but in liquidation per IBBI) both are shown. Re-verify on the live registry by CIN before a lending decision.
- **B-44 Untrusted links, uploads and redirects** → render data-supplied URLs only through `safeExternalUrl` (http/https only), follow return paths only through `safeInternalPath`, cap upload and decompressed sizes, and keep the CSP strict (`web/security-headers.ts` = `firebase.json`). See SECURITY.md.
- **B-45 Vulnerable dependencies (SCA)** → CI fails on any known vulnerability in production dependencies (`npm run audit:prod`); Dependabot proposes weekly updates. Development-only advisories without an upstream fix are listed and accepted in SECURITY.md until fixed.
- **B-46 Public-records bundle served without sign-in** → the deploy workflow publishes `web/public/graph-lab/` (~5 MB gzip, public-source data) with Hosting, so `/graph-lab/**` is downloadable by anyone and bypasses the sign-in + App Check gate of `publicData` (`/data/**`). Accepted as a bridge until the cloud feed is live; then remove the deploy step and the `/graph-lab/` fallback in `web/src/lib/graph-lab.ts`.
- **B-46 Incremental listing misses** → an incremental listing stops at the first page of already-known items, so an edit or late insertion deeper in a source is not seen until the next full relist (IBBI, NFRA, SFIO weekly; RBI and the SEBI full index monthly; `FULL_RELIST_EVERY_DAYS`). Sources that do not publish newest-first would lose items between relists: check the order before adding an adapter to the incremental set.
- **B-47 Source layout change and partial failure** → a first page that parses to zero rows (or returns 404) for a collection we already hold, a listing that returns nothing, or a complete relist that loses more than half of the listed items (from 20 items up) fails that source and leaves its listing and state untouched (never an empty or truncated overwrite); `--allow-shrink` accepts a real drop. Sources run independently; the run summary records `failed` with the step and the exit code is 1. Records that vanish from a source are flagged `removed` in the delta report and kept (soft delete); capped samples (`maxItems`) never report removals.
- **B-48 Concurrent ingest runs** → `acquire` reads, merges and writes listings, so two runs on the same data folder would lose updates. A lock file (`data/interim/acquire.lock`) allows one run at a time; a lock older than 12 hours is treated as a crashed run and replaced. The local lock does not cover two machines sharing a bucket: the cloud job needs its own lock (planned with the Cloud Run job).
- **B-50 Publish pointer and rollback** → the app only ever sees a bundle that passed every publish gate (required tables non-empty, no table dropping more than 20 % against the published build, bundle ≤ 48 MB compressed, newer than the published one, no seed case lost). Bundles are written once into `versions/<builtAt>/`; publishing is a compare-and-swap of one `current.json` pointer, so a concurrent publish fails instead of overwriting; 14 versions are kept for rollback. New deployments run as a dry run (separate `dry-run` channel and `_dryrun` dataset) until the owner enables publishing.
- **B-51 Cloud leases and concurrent writers** → in the cloud, Firestore leases (`ingestLocks/{acquire-<source>|build}`, expiring after the task timeout + margin, removed by a TTL policy) replace the local lock file; a run that finds a live lease records the source as failed (`lease:`) and changes nothing. Listing writes additionally use a Cloud Storage generation precondition, and raw evidence is create-only, so even a lease bug cannot lose an update or overwrite evidence.
- **B-53 Paced backfill** → the per-run document cap (`FUNDTRACE_MAX_DOCS_PER_SOURCE`, 300 per source in the cloud) counts only items that still need work (not yet resolved, missing a stored document, or changed in this run), so a backlog moves forward a little every day instead of re-selecting the same items.
- **B-49 Agent authority** → the ingestion agent runs under its own service account that can only read the buckets and BigQuery; its code has five tools (three read-only lookups, `propose_action`, `submit_review`) and no way to fetch URLs or write pipeline data. Findings and severities are computed by code; the model writes the summary and may propose actions from a fixed allowlist, each of which waits for the owner's approval. The only automatic action is `rerun_source`, decided by code for transient network errors, at most once per run. Model output is schema-validated, verdict words are rejected, tool calls (8) and input size are capped, healthy days skip the model, and `INGEST_AGENT_ENABLED=false` turns the model off.
- **B-52 AI extraction** → model-extracted claims are kept in shadow (`evidence_claims_ai_shadow`, create-only objects under `interim/ai/claims/`) and never feed the graph or the app until the quality gate (`ingest/eval/README.md`: ≥ 30 hand-checked documents, organisation precision ≥ 0.90, CIN and amount precision ≥ 0.95) passes and the owner approves. Grounding by code: organisation names and amounts must appear in the document text, CINs must be printed in it, individuals are dropped (B-38), amounts are converted to integer paise by code (B-01), evidence status comes from the source classification (B-36). Per run at most 50 documents, 10 pages and 30k characters each; off by default (`FUNDTRACE_AI_EXTRACT_ENABLED`). A new prompt version or model re-extracts into a separate folder; nothing is overwritten.

## Synthetic data (`ingest/src/synth`, `packages/shared/src/synth`)

- **B-54 Synthetic and real data separation** → generated loans, transactions and flags are fictional test data. Every record carries `synthetic: true`; every name starts with `SYNTH `; URLs use `example.invalid`; amounts are INR paise integers. The generator writes only to its own folder (`data/synthetic/`) and never into `data/raw`, `data/processed` or `data/registry` (`assertSafeOutputDir`), and loads only into a BigQuery dataset whose name ends in `_synth` (`assertSynthDataset`). Generated text is scanned for real-looking identifiers (PAN, CIN, IFSC, 12-digit numbers, emails, outside URLs). The app must label any such data "Synthetic test data" and never show it as real. The synthetic enums mirror the web app's and a web test fails if they drift.
- **B-55 Ground truth is not evidence** → results on synthetic data prove the plumbing only; no accuracy is quoted from them (the generator wrote both the data and the labels), and one archetype (`dormant_burst`) is held out of pattern writing. The scorer never reads `truth.jsonl`: the input port (`ingest/src/risk/fileInputs.ts`) has no truth field, and only the evaluation harness (`ingest/src/risk/evaluate.ts`) reads it. Tests: `fileInputs.test.ts` ("never reads truth.jsonl": a corrupted or deleted truth file gives identical inputs), `evaluate.test.ts`.

## Risk scoring (`packages/shared/src/risk/scoring`, `ingest/src/risk`)

- **B-56 Missing or stale inputs are not low risk** → public data older than `stale_after_days` (7, owner's decision) on the scoring day, or any input the loader could not read, marks the score `stale_inputs`; such a run never counts towards a band step-down (and does not reset the count), and the "what changed" text says a lower score is not an improvement. An empty, all-retired or refused pattern library scores the pattern layer 0 and marks the score `no_patterns`, worded as "its 0 is not low risk"; a refused library or a bad pattern is a run finding, never a crash. Tests: `score.test.ts` (7 days fresh, 8 stale; missing input), `decide.test.ts` ("stale run neither counts nor resets"), `patternLayer.test.ts`, `replay.test.ts`, `reasonText.test.ts`.
- **B-57 Score history is immutable** → BigQuery `risk_scores`, `risk_alerts` and `risk_patterns` are append only, partitioned by `as_of`; a correction is a new row, never an update. The load job id is the table, the IST day and a hash of the rows without the run id and times, so a retried day (whatever its run id) loads nothing new (B-24). Firestore `synthRiskAlerts/{alertId}` is created once (`create`, never `set`), with the alert id = loan + hash of the alerted reason keys; `synthRiskLatest/{loanId}` is the only document rewritten, and it keeps the state from before its day so a retry gives the same result. A day earlier than the stored one is refused (`ScoringOrderError`; the replay CLI is for past days). Clients cannot write either collection. Tests: `daily.test.ts` (retry of the same day, earlier day refused), `scoreWriter.test.ts`, `cloud/scoreTask.test.ts`, `scoreStore.emulator.test.ts`, `firestoreRules.emulator.test.ts`.
- **B-58 A score is a lead, not a verdict** → bands use the app's wording only (Routine review, Needs attention, Urgent review; `RISK_BAND_LABELS`); reason text is templated, neutral and passes `violatesWording` (never "fraud"); evidence statuses are shown as found (B-36); no adverse action is taken automatically from a score, band or alert (AGENTS_PLAN.md, Autonomy). Tests: `reasonText.test.ts` (every reason code renders neutrally; the band labels).
- **B-59 Prepayment or catch-up** → a repayment of at least `prepayment_min_multiple` usual EMIs is a prepayment only when no EMI is past its grace period unpaid on that day; then it pays no EMI slot, counts towards the loan amount, and the usual EMI is worked out again from the repayments after it. The same payment while an EMI is overdue stays a catch-up, so a missed EMI is never hidden. The first repayment is never a prepayment (no usual EMI yet). Off (`null`) in settings v1 and v2, so their stored scores replay unchanged (B-24). Open: a segment after a prepayment with one or two repayments has a weak usual EMI, so a short payment there can read as normal. Tests in `behaviour.test.ts`.

## Agents: pattern miner and risk explainer (`ingest/src/miner`, `ingest/src/explain`)

- **B-60 One case, one vote** → support counts distinct cases, never entries: the four largest cases hold 72% of the timeline entries and must not create a pattern alone. The model never sets a number; every number in its wording must be one the code computed (`ai/outputChecks.ts`). Tests: `candidates.test.ts` (an 80-entry case gives support 1), `miner/agent.test.ts` (a changed number is rejected).
- **B-61 Patterns are approved by a person** → the miner writes only `patternProposals` (`create`, deterministic ids; the same candidate on the same input is never proposed twice, even after a decision). Only the `decidePattern` callable, called by a signed-in person with the `admin` claim, writes `riskPatternLibrary/current` and an immutable `riskPatternLibrary/v<n>` copy, in one transaction, bumping `library_version` and the content hash; a hand-edited library (hash mismatch) is refused. An expired proposal can be rejected, not approved. The mock provider and the kill switch (`FUNDTRACE_MINER_ENABLED=false`, the default) store no proposals. Caveat: `roles/datastore.user` is project-wide, so the cloud does not stop the miner's account writing other collections; its code and tests do. Tests: `functions/src/services/patterns.test.ts`, `decidePattern.test.ts`, `cloud/mineTask.test.ts`, `miner/store.emulator.test.ts`, `firestoreRules.emulator.test.ts`.
- **B-62 AI wording is a convenience, not evidence** → the risk explainer's sentence is stored beside the alert in `synthRiskExplanations/{alertId}` (created once), never inside it, because an alert is never rewritten (B-57). It is shown only with the label "AI-written summary of the recorded reasons" and with the alert's recorded reasons under it; if they disagree, the reasons are right. Code checks every sentence: at most 400 characters and two sentences, numbers and dates only from the input, only the placeholders given (ids never reach the model, B-38), the top reason named, an allegation never worded as a finding (B-36), no verdict words. One explanation per alert: a new prompt version applies to new alerts only. At most 30 alerts per run, most urgent first; the mock and the kill switch (`FUNDTRACE_EXPLAIN_ENABLED=false`, the default) store nothing. Tests: `explain/checks.test.ts`, `explain/explainer.test.ts`, `cloud/explainTask.test.ts`, `explain/store.emulator.test.ts`, `getRiskScores.test.ts`, `web/src/lib/cloud/risk-scores.test.ts`.
- **B-63 Patterns from hand-picked defaulters** → the 23 seed cases were chosen because they defaulted, so a pattern's support says it appeared before known failures, not that it predicts them. Lift is measured only against entities already named in adverse records (`miner/lift.ts`); no precision or hit rate is quoted, and the miner's prompt forbids claiming accuracy. The first real run found no candidates (checkpoint 1). Tests: `lift.test.ts`, `candidates.test.ts`, `miner/agent.test.ts` (a summary with an invented rate is rejected).
- **B-64 Application data sent to Gemini** → only on a reviewer's click (`analyseApplication`), after the AI allow-list and the daily limit; the browser leaves out unreadable and empty fields, masks identity, account, phone and similar fields (B-16) and drops documents beyond 20,000 characters (counted and shown). Names and amounts are sent, because the analysis compares them across documents: **open for the owner** whether names should be masked too. The model's facts are kept only when they quote a field that was sent, notes only for findings that were sent, and verdict words are withheld (B-58). The AI Studio key must be on a billed project (free-tier prompts may be used to improve Google's models). Tests: `functions/src/services/applicationAnalysis.test.ts`, `functions/src/callable/analyseApplication.test.ts`, `web/src/lib/application-analysis.test.ts`.
- **B-65 Branch scope hides other branches** → the sidebar's branch switcher sets the default branch filter for every list, the counts and the dashboard (`web/src/state/scope.ts`). A scoped view must never hide urgent work silently: the switcher shows how many **Urgent review** alerts are open in other branches (`navCounts().urgentElsewhere`), and "Clear all" on Alerts still means every branch. Branch officers are locked to their own branch, as before. An unknown stored branch id falls back to all branches. Tests: `web/src/lib/nav-counts.test.ts`.
- **B-66 Record facts sent to Gemini by the copilot** → FinRakshak Copilot (`assistRecord`, docs/COPILOT.md) runs only on a click, after the AI allow-list, the burst limit (6 a minute) and the shared daily AI limit (B-15). The browser sends one record as at most 60 numbered facts (label 120 / text 400 characters); PAN, Aadhaar, account and phone numbers are masked first (`web/src/lib/assist/pack.ts`, B-16). Names and amounts are sent, as for B-64. The officer's question goes in its own delimited block, and the facts are marked as data, not instructions. Code keeps a model statement only when it cites facts that were sent, every number in it appears in those facts or the record title, and it uses no verdict word (B-58). Everything removed is counted and shown with the answer. Logs carry counts only. In a demo session no model is called: answers are built from the same facts by fixed rules, pass the same check, and are labelled **Simulated demo output**. The grounding check exists twice (`packages/shared/src/assistGrounding.ts` and its runtime copy `functions/src/services/assist.ts`); both run `packages/shared/src/assist-grounding-cases.json`. Tests: `assistGrounding.test.ts`, `functions/src/services/assist.test.ts`, `functions/src/callable/assistRecord.test.ts`, `web/src/lib/assist/simulate.test.ts`.
